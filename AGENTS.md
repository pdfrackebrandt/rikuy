# Working on Rikuy: a guide for coding agents

Rikuy is a LaTeX editor in the browser: you type on the typeset page and edits patch the
`.tex` source; real TeX Live 2026, compiled to WebAssembly, runs in a Web Worker to make the
PDF. Read this file first, then `HANDOFF.md` for the work in flight (several agents build Rikuy
and any of them may stop mid task: it says what is half done and how to carry it on), then
`docs/ARCHITECTURE.md` for how the parts fit, and the table at the top of `PLAN.md` for where the
project stands. Everything below was true when written; if
a command fails, trust the code and fix this file.

## Setup

- node 22, then `npm ci`
- Python 3 with `pip install lz4 playwright numpy pypdf python-docx` (CI pins `playwright==1.56.0`; the arXiv corpus workflow installs `dev/arxiv-requirements.txt`, pinned by hash; where the system Python refuses pip, as Ubuntu 24.04's does, first `python3 -m venv .venv && . .venv/bin/activate`), then `python3 -m playwright install chromium` (the scripts use `/opt/pw-browsers` instead when that folder exists); `poppler-utils` for the comparisons
- a C compiler, so `tex/build_tree.py` can build `tex/native/t1crypt.so` on first use (without one it still works, many times slower)
- for `tex/build_tools.sh`: Ubuntu's `emscripten` 3.1.6 package and node; `git`, `curl`, `make`, `pkg-config`, `xz`, `bzip2`, `dpkg-deb`; for Mesa `meson`, `ninja`, `bison`, `flex` and Python's `mako`; for the native ECL that builds xindy's `gcc` with `libgmp-dev` and `libgc-dev` (the script's header has the list)
- for comparisons with a desktop: `dev/fetch_tl26.sh` (about 6 GB into `/opt/tl26`, or the folder `TL26` names) and `xvfb`

## Where things go

- A new command: an entry in the batch's own `src/cmd/<area>.js` (`register({...})`, fields in `src/commands.js`'s header), placed in a tab and group of `src/ribbon/order.js`; its methods in that module's `methods` (a name another module or the app has already throws as the page loads: `joinMethods`). The module is loaded under node too, by the build (llms.txt, `controls.json`): it touches no `document`, `window` or `navigator` as it loads, only inside what it registers. Nothing else to edit: the ribbon, the keys, the search box, the right click menu, `controls.json`, llms.txt's list and `test/agent.py` follow. Its tests use `roundtrip()` of `test/browser.py` (GAP section 0's rule as one call).
- A new unit test: a `test/<name>.test.mjs` file, added to the `test` chain in `package.json`, or a case in the file that already covers the module. A new browser test: a `test/<name>.py` in the style of `test/browser.py` (its helpers `open_page`, `load_doc`, `click_text`, `src`, `check`), named in the Commands table above and, if CI should run it, in `.github/ci-shards.json` (no TeX: its command in any shard, then `python3 dev/ci_balance.py --write` deals the shards again and writes ci.yml's matrix; a script of `test/` in no shard and not named in that file's `elsewhere` fails the `editor` gate) or `.github/tex-shards.json` (needs `dist/tex`; `dev/ci_balance.py --list .github/tex-shards.json --write`, and its `paths` name the files whose change makes a pull request run TeX).
- A TeX tree without the 3 GB of downloads: every TeX run on `main` keeps its `dist/` as a workflow artifact. `gh run download $(gh run list --workflow tex.yml --branch main --status success --limit 1 --json databaseId --jq '.[0].databaseId') --name rikuy-dist --dir dist` gives a full `dist/` with `dist/tex/`; `npm run build` then replaces the page in it and leaves `dist/tex/` alone.
- What an agent using Rikuy (not changing it) reads: `llms.txt` and `llms-full.txt` on the site, written by `llms()` in `build/app.mjs`; the scripting surface is `window.rikuy.api` (`src/app.js`), and `test/agent.py` checks that an agent finds every control by its name. The agent tools are one table, `TOOLS` in `src/agent.js`: a new tool goes there with its schema and hints, and WebMCP, `rikuy.api.callTool` and llms.txt follow; a command that takes arguments declares their JSON schema as `args` (or in `ARGS` there, checked against what an agent passes); one that deletes or reads the clipboard is added to `ASKS` (the person is asked), one that sends the document out of the page, opens an address or leaves the open document to `PERSON` (no tool runs it: the person presses it).
- New CSS for motion goes in `src/motion.css`, colours, sizes and durations as `--rk-*` tokens of `src/tokens.css` (`docs/handoff/FUTURE.md` says where app.css moves to them).
- What ships and deploys: a merge to `main` runs `tex.yml`, and `deploy.yml` puts that run's `dist/` on Cloudflare Pages (`docs/HOSTING.md`). Nothing else publishes.

## Handing off

Rikuy is built by several agents (Claude, Grok Bot, Pedro himself), and any of them may stop in
the middle of a task. Work is never kept only on one machine:

- Commit each finished step on its branch and push it; on an unmerged branch a commit
  "WIP: done X; left Y" is fine.
- Stopping mid task, with changes not ready to commit or a merge half done:
  `sh dev/wip.sh [worktree] "done X; left Y"` pushes the worktree as it stands to `wip/<branch>`
  (a fast forward each time; the worktree is not touched). `HANDOFF.md` says how to pick one up.
- Every open pull request ends with a `## Handoff` section (state, next step, where its review
  is); whoever stops updates it, and `HANDOFF.md`'s table when the list changes.
- A review is a file, `docs/reviews/<batch>.md`, with each verification appended to it.
- Never force push; a branch that must take main merges main.

## Checking a change

Pick the checks by what you touched, and run them before you call it done:

- `src/agent.js`, `src/webmcp.js`, `src/a11y.js` or the renderer's roles: `npm run test:agent`; `src/motion.js`, `src/caret.js`, `src/motion.css`, `src/tokens.css`: `test/motion.py` (and `dev/bench_typing.py` for anything on the typing path)
- `src/`: `npm test`, `npm run test:browser`, `npm run test:tabs` and `test/ribbon.py` for the ribbon, its commands, keys, search or menus, `test/consistency.py` for anything the ribbon, the tab row, the title bar or the status bar draws (its sizes, type, colours, spacing), `test/font.py` for character formatting (`src/cmd/font.js`, `src/charfmt.js`, the inline rows of `model.js`), `npm run test:agent` for any control, dialog, name or `build/app.mjs`'s guides (an agent finds controls by the names listed in `llms.txt`: renaming one is a change to a public interface), and `npm run test:corpus` for anything in the model or parser; `test/scripts.py` for direction, the page's fonts or `scripts.js`; `npm run test:offline` and `test/launch.py` for `pwa.js`, `sw.js`, `tex.js` or `build/app.mjs`
- `tex/engine.js`, `shell.js`, `tools.js`: `npm run test:engines`; for a fix found on a document, compile it with `dev/texrun.py` before and after; for the compile loop or the preamble's format (`PRE`), `test/preamble.py` and `dev/bench_same.py`
- the tree or packs: `cd dist/tex && find . -type f | sort | xargs sha256sum | diff ../../dev/dist-manifest.txt -`; any difference must be one you meant

## Rules that hold everywhere

- Every download is pinned by hash; a new one gets its hash in the script that fetches it, and a line in `SOURCES.md` if it ships.
- `dist/tex` is reproducible: the same inputs give `dev/dist-manifest.txt` byte for byte. Update the manifest only together with the change that moves it.
- Programs in `tex/vendor/` are build outputs of `tex/build_tools.sh`; never edit or replace them by hand.
- Result files (`dev/*-results.jsonl`) are replaced by a full run, never appended to by hand.
- Commits follow `PLAN.md`'s rules: one commit per finished task, its message saying what changed and the evidence; no status commits (but `HANDOFF.md`, and "WIP:" commits on an unmerged branch, see Handing off).
- Code comments say why, in plain words; keep the style of the file you are in.

## Pitfalls already met

- Rikuy was called Galley at first. Names built into the programs and the packs (`galley_main`,
  `GalleyAsy` and the other factories, the `galley` section of every pack), the keys of what
  browsers keep (`galley.project.v1`, the `galley` and `galley-tex` databases), field names in
  `dev/*-results.jsonl` and the native layer in `tex/native/` keep that name: renaming them would
  change every build output or lose people's documents. Everything else says Rikuy.

- Ubuntu's Emscripten 3.1.6 outputs need `node --no-experimental-fetch` to run under node 22.
- The package is an ES module (`"type": "module"`): to `require()` an Emscripten `.js` from node, copy it to a `.cjs` name or a folder outside the repository first.
- `tex/build_tree.py tools` must run with the same `RIKUY_WORK` the tree was built from; another one changes the Python wheels and so the manifest.
- Programs built for Rikuy are entered through `galley_main` (`tex/native/galley_main.c`) and run many times in one instance: `tools.js` puts their memory back after every run, and lets a program go when a run leaves it above 1 GiB.
- asy runs twice per figure: a rehearsal that only notes the labels it will ask TeX about, then the real run (`tex/README.md`). Anything asy starts fails during the rehearsal on purpose.
- asy has no fork here: it renders 3D pictures in place and then copies its memory back (`tex/native/patch_asy.py`); keep that when touching its rendering.
- The desktop's asy renders 3D through a window: run its comparisons under `xvfb-run -a`.
- The copy the maintainer publishes on claude.ai is built with `RIKUY_SHARE` set to that artifact's address (`https://claude.ai/artifact/W7htGmmfauM4Z3KpjV9vzK`, which opens for others only once it is shared), because a page in a frame cannot see its own address; a copy on your own site needs no `RIKUY_SHARE`. Run the browser tests on a build without it (`test/share.py` expects links to the page itself).
  That build is also the only one without the installed app (service worker, manifest, `lib/`).
- The browser tests that wrap `rikuy.html` (`browser.py`, `serve.py`) never start the installed
  app: it starts only in a document with `<meta name="rikuy-app">`, which only `index.html` has.
  `test/offline.py` and `test/pages.py` test it. A service worker answers the requests of the pages
  it controls; a test that changes what a server returns must go through it (or a new context).
- The page runs under a strict Content Security Policy (`build/app.mjs` `policy`; `test/serve.py`
  and `browser.py`'s `open_page` serve it, read from `dist/_headers`): scripts only from the page's own
  site and the page's one inline script by its hash, WebAssembly but no eval, `connect-src 'self'`
  (the worker, which shares the policy, can fetch only files next to the page; git goes through
  the site's own proxy, `/git`, a Pages Function: `functions/git/[[path]].js`, `src/gitproxy.js`).
  A test whose own servers stand in for hosts passes them to `open_page(connect=[...])`;
  `test/gitproxy_server.mjs` runs the proxy's code locally (`test/git.py`). Code that needs `eval`, `Function`, an
  inline script or an `on*` attribute fails there. Playwright's `wait_for_function` with an
  expression evals it in the page each time it polls; `browser.py` hands every one over as a
  function, so import it before Playwright starts. A live figure runs in its own document
  (`widget-<hash>.html`, `src/widget.js` `runWidget`).
- The browser tests' helpers wait on conditions, not on time: `open_page()` returns once
  `rikuy.ready` has settled, `load_doc()` once the pages are drawn (`rebuild()` is synchronous),
  `click_text()`, `select_text()` and `place()` once their `selectionchange` has reached the page's
  handlers, and `roundtrip()` once each step's edit has landed (`landed()`). After any other step,
  `settle(page, ms)` (ms: the time the step once slept): the next frame, and the page's timers due
  within 80 ms (`SOON`: the ribbon's refresh after the caret moved), seen through the timers every
  context of `open_page()` tracks (`TIMERS`); `settle(page, ms, full=True)` waits for every timer due
  within ms instead (a refit after a resize, a debounced push), and `after=` names the page's own
  debounced work to wait for whenever it is due (`REPAINTS`: Track Changes' marks and comments,
  repainted 180 and 200 ms after every rebuild). Work that is no timer (a module, a worker, a fetch)
  gets a condition of its own: `until(page, fn)`, which leaves a promise that never comes to the
  next check; `ready(page)` after a reload (init through, not only the boot screen gone);
  `stored(page)`, every IndexedDB write the page opened come back (`TIMERS` counts them too);
  `saved(page)` before a reload that must find an edit; `kept(page)` for a tab hidden or shown
  (its copy and IndexedDB's agree). A fixed `wait_for_timeout`
  is for where the time itself is under test, with a comment saying so. `RIKUY_WAIT_SHADOW=1` waits
  the old time as well after each such condition and prints `SHADOW` with what still moved and the
  timers then due; `RIKUY_CHECK_LOG=file` writes what each check saw, so a fast run and a shadow run
  can be compared check by check (measured times written as `<t>`, and the detail of a check whose
  name gives a time in ms, a latency or a long task as `<timed>`). `open_page()` shares one Chromium per process: each call
  gets a context of its own, and the browser it returns closes that call's contexts, not the
  shared one.
- This machine's Python may be linked with zlib-ng, whose gzip bytes differ from stock zlib's: packs
  built with it get other names than `dev/dist-manifest.txt` has. To make the manifest here, run
  `build_tree.py` with Ubuntu 24.04's `libz.so.1.3` in `LD_PRELOAD` (CI's Python uses that one).
- The packs for scripts other than Latin (`x` in the index: Chinese, Japanese, Korean, Arabic, Hebrew, India's, Thai, Sinhala) are not in the artifact: build and test them on
  the hosted build; `tex/README.md` says what they hold.
- The published artifact may hold 256 MB; `PLAN.md` gives the current size. It has no room for
  pandoc: build that copy with `RIKUY_NO_WORD=1` (and `RIKUY_WORD_HOST` naming a copy with Word).
- `test/fixtures/word-fixture.docx`, `word-rich.docx`, `word-chinese.docx`, `word-arabic.docx`,
  `word-mixed.docx`, `word-hindi.docx`, `word-indic.docx`, `word-japanese.docx`,
  `word-korean.docx`, `word-hebrew.docx` and `word-scripts.docx` are `test/word_fixture.py`'s
  output (`python3 word_fixture.py out.docx`, and with `rich`, `chinese`, `arabic`, `mixed`,
  `hindi`, `indic`, `japanese`, `korean`, `hebrew` or `scripts` after it), kept so `npm test`
