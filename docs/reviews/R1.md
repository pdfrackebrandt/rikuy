How the page breaks were judged: Chromium here sets wrapped text with other line breaks than TeX (paragraph P1 of p1/main.tex is 5 lines on the page, 4 in TeX), which swamps any page break comparison on ordinary wrapped text (corpus agreement is about 25% on main and on R1 alike). ## High

### H1. The topskip allowance plus the plan's 1.5 px tolerance overfills pages: memoir document regresses from 12 pages that match TeX to 10
- Repro: /tmp/review-r1-out/nw/memoir/main.tex (memoir, 4 chapters with sections and equations, short lines). `RIKUY_DIST=<dist> python3 pb.py nw.list resnw <tag> [compile]`, then `python3 cmp.py resnw`.
  TeX: 12 pages (openright, blank pages 6 and 10). Main: 12 pages, every page start equals TeX's (9/9). R1: 10 pages, 3/8; chapter 3 starts on page 5 instead of 7 and every later page is off by two.
- What happens: on page 3 (chapter 2's opening page) R1 puts two lines of the next paragraph at the foot (plan `used` 552.2 against H = 552, accepted by `cost <= avail() + EPS`); TeX has no room for them, so it sets them on page 4, which makes chapter 2 need page 5, and openright then pushes everything two pages. Main had 528.8 used and no room.
- Cause: src/layout.js:289 `const H0 = this.g.th * this.px + top` now makes the capacity exact for text lines ((textheight - topskip)/baselineskip + 1), but the split test at src/layout.js:546 still adds `EPS` (1.5 px) on top. Before R1 the missing (baselineskip - topskip) absorbed that tolerance; now a page may be 1.5 px fuller than TeX's page can be.
- Fix (tested: fix/src/layout.js): take the tolerance off where the allowance is added,
  `const H0 = this.g.th * this.px + top - (top ? EPS : 0), HL = this.g.tw * this.px + top - (top ? EPS : 0);`
  Result: memoir back to 12 pages, 9/9; the 26 no-wrap documents 214/303 page starts agreeing (R1 210/301, main 152/304); page count equal 17/26 (R1 16, main 16); corpus and synthetic wrapped documents 199/799 (R1 200/799, main 180/806), no document losing more than one page start.

## Medium

### M1. A tabbing far down a big file loses letters, and the incremental and full builds disagree there
- Repro: `node /tmp/review-r1-out/node/tbbudget.mjs` (2 MB file: a plain paragraph, 2 MB of comment lines, ten tabbings using `\=`). With the budget left at 10, one letter typed in the first paragraph: the incremental build (fast path taken) keeps the tenth tabbing as `Name9 | Value | Note`; the full build of the same text gives `Name9 | alue | ote` (`sameModels` false). Any file where the sum over its tabbings of (offset + body length) passes 20 M, e.g. a 2 MB thesis with ten tabbings near its end, draws the later ones with the first letter after each `\=` eaten (the parser's macron accent), and reload shows something other than what typing showed.
- Cause: src/model.js:2245, the second read pads the body with `' '.repeat(nd.be)` and spends a per build budget of 2e7 that depends on every earlier tabbing's offset; the incremental path (src/model.js incremental) moves the tabbing's unit instead of rebuilding it, so a keystroke that moves offsets across the budget is never re-read.
- Fix: no padding and no budget: parse `body` alone and add `nd.be` to the offsets of the nodes it returns (one recursive walk over the numeric offset fields, as OFFSET_KEYS lists them); or, better, have the parser (parseJS and parse.cc together) read `\=` inside `tabbing` as a control symbol with no argument, which makes the second read unnecessary.

### M2. A Word file written by LibreOffice (Normal without w:default="1") imports with every paragraph wrapped in `spacing{1.15}` and hand set left alignment lost
- Repro: /tmp/review-r1-out/word/lo/justified.docx (python-docx justified document saved again by LibreOffice 24.2). `node imp.mjs /home/claude/wt-r1-verify <file>` writes `<file>.branch.tex`: each section's body paragraphs, justified and left aligned alike, sit in `\begin{spacing}{1.15} … \end{spacing}` (one per section, split by every heading), `\usepackage{setspace}` is added, and the three paragraphs set left by hand get no `flushleft`. Main imports the same file with plain paragraphs.
- Cause: LibreOffice writes `<w:style w:type="paragraph" w:styleId="Normal">` without `w:default="1"`, so `S.normal` (src/docx.js styleInfo, ~line 589) stays undefined; `styled(C, null, …)` then returns null and `C.base` (src/docx.js paraFix, ~line 863) takes no spacing (100) and `jc` 'left'. Each paragraph's own style (Normal, line 276) then differs from that base (flag 4), and left equals the base (no flag 1). The document spacing at src/docx.js ~685 is missed for the same reason.
- Fix: in styleInfo, `if (!S.normal) S.normal = [ids].find(id => id === 'Normal' || name(id) === 'Normal')` (the paragraph style whose id or name is Normal) before anything reads it.

## Low

### L1. Hand written tabbing with `\+` and `\-` drawn without its indentation
- Repro: `node /tmp/review-r1-out/node/tbfirst.mjs`: `\+ Indented \> x\\` and `\- Back` come out as lines starting at stop 0; TeX starts the line after `\+` at the first stop (the usual way pseudo code is indented in tabbing).
- Cause: src/model.js:2262 drops `\+ \- \<` with `continue`. Fix: keep a margin count per line (incremented by `\+`, decremented by `\-`, `\<` for one line) and give the line's first cell the start of that stop (src/layout.js tabStops already has the stops).

### L2. Twocolumn articles treated as ragged bottom when weighing club and widow lines
- src/pagesrc.js penalties: `out.flush = !!(cls && cls.twoside)`; article.cls, report.cls and book.cls set `\flushbottom` under twocolumn. Fix: `cls.twoside || cls.twocolumn` (KOMA and memoir have their own rules; keep \raggedbottom/\flushbottom winning as now).

### L3. A landscape section in Word keeps the portrait page's footer distance
- /tmp/review-r1-out/word/exp-sections.docx (from exp.mjs): the landscape section has `w:bottom="1786"` (the portrait right margin turned) but `w:footer="2393"`, larger than its bottom margin, so Word moves the body up or the footer into the text. src/wordpage.js sectOf, the land branch of pgMar. Fix: for a turned section, `w:footer` at most the new bottom margin less a line (and `w:header` likewise against the new top). Everything else in the sections checked out: python-docx reads five sections (new page, continuous, continuous, landscape new page, new page), LibreOffice prints the two column part in two columns and the landscape page turned (A4 841.89 x 595.3), and an unchanged round trip through planImport changes nothing; a coauthor's edit in the columns and between the parts comes back to the right lines.

### L4. Inside landscape pages with a footnote and an [h] float the page cuts differ from TeX's

New defects (none High or Medium):

- **N1, Low: words in a brace group right after `\<` or `\+` vanish from the page.** This was also in 6bb2975, and L1's fix keeps it. node/small.mjs: `Beta \<{\small S} x` draws `Beta x`, and `\+{\em E} x` draws `x`. Cause: the parser can give `\<` and `\+` the following group as an argument (for `\<{y}` it reads one), and the tabbing loop (src/model.js, the `+`/`-`/`<` branches) does `continue` without keeping `n.args`. Fix: push the nodes of `n.args` into the current cell before `continue`.
- **N2, Low (latent): `shiftNodes` does not move `ne`.** The parser sets `ne` on 21 of the 70 nodes in a typical tabbing body. src/model.js NODE_OFFSETS lists `s e is ie bs be es nameEnd` only, and `ne` is read by lists.js (`\item` head), model.js:2470 (an empty item's placeholder) and picture.js. I found no path from a tabbing to those readers (a list inside a minipage inside a tabbing cell is not flowed), so nothing is mis-mapped today. Fix: add `'ne'` (and any other numeric field the parser sets) to NODE_OFFSETS.
- **N3, Low (hostile files only): `shiftNodes` stops after 1e6 visits but uses the partly moved tree.** The old 200 000 character limit on a tabbing body is gone, so a stranger's tabbing of about a megabyte of `\>` leaves its later nodes at body-relative offsets. Typing in those cells would edit near the start of the file. Fix: when the cap is hit, fall back to `nd.nodes` (the parser's own reading), or drop the cap, since the walk is linear.

Verdict on 965a756: merge. Every finding is fixed as stated, with the numbers I measured on my own harness, and the fixes caused no regression on page breaks, Word import or the incremental build. N1 to N3 are small and can follow (N2 and N3 are one line each in shiftNodes).
